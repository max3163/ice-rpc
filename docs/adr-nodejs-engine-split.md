# ADR — Extract the reusable Node.js engine (`ice-rpc-nodejs`)

- **Status**: accepted and implemented
- **Scope**: the Node.js gateway ([`gateway_nodejs`](../gateway_nodejs)) and the
  new crate [`ice-rpc-nodejs`](../ice-rpc-nodejs)
- **Related**: [`docs/nodejs-gateway-api-v2.md`](nodejs-gateway-api-v2.md) (the
  JavaScript contract, unchanged)
- **Plan**: [`plans/design-2-gateway-engine.md`](../plans/design-2-gateway-engine.md)

## Context

The Node.js gateway depended on the **example** crate `common`:

- [`gateway_nodejs/src/services.rs`](../gateway_nodejs/src/services.rs) hard-coded
  `common::ConfigServiceProxy`, `common::ContextServiceProxy`, …;
- [`gateway_nodejs/Cargo.toml`](../gateway_nodejs/Cargo.toml) declared
  `common = { path = "../examples/common", features = ["napi"] }`.

A precompiled addon cannot serve an arbitrary service set: the rkyv ↔ JSON
conversions of each service are generated by `#[service]` and must be linked into
the `.node`. The service set is therefore a **compile-time** property of the
addon. The example list made the shipped artifact depend on a non-shipped example
crate — a distribution dead end.

Everything else in the gateway was already generic; the coupling was localized to
the service list.

## Decision

Split the gateway into two crates:

- **`ice-rpc-nodejs`** (rlib, published on crates.io): the reusable engine — the
  JS bridge, the lifecycle, the consumer dispatch, the error codes and the
  `GatewayService` table. It holds **no service** and references no `common`.
- **`gateway_nodejs`** (cdylib, in-repo only): the **reference addon**. It names
  its services through the [`gateway!`](../ice-rpc-nodejs/src/macros.rs) macro,
  which also emits the eight N-API functions.

The seam is a static table the addon builds from its proxy list:

```rust
pub struct GatewayService {
    pub name: &'static str,
    pub provide: fn() -> BoxFuture<'static, ()>,
    pub invoker: fn() -> BoxFuture<'static, Option<Arc<dyn JsonInvoker>>>,
}
```

Two function pointers per service, because the `ServiceLocator` resolves a proxy
**by concrete type**, and only the addon knows those types.

### Why a macro rather than runtime discovery

The alternative — auto-discovery through a link-time slice, as the `monitoring`
decoders do — was rejected: it would advertise **every** service linked into the
binary, dropping the explicit-subset property the v2 contract deliberately chose,
and it would require the `#[napi]` functions to live in a linked rlib, an
unproven napi-rs behaviour. The macro keeps the subset explicit, the N-API surface
in the cdylib, and the list a single line.

## Reusability for another gateway type

The crate is **Node-specific**. The transport-agnostic half already lives in
[`ice-rpc::json`](../ice-rpc/src/json.rs): `JsonInvoker`, `JsonDispatcher`,
`JsonCallStream`, `ReadMode`, `read_json`. The HTTP gateway already consumes that
`JsonInvoker` with no Node code, and a future Python/WASM gateway would implement
its own `JsonDispatcher` on `ice-rpc::json` — it would reuse nothing else from
`ice-rpc-nodejs`. The crate is named for what it is.

## Consequences

- A third party builds **their own** addon without cloning the workspace: depend on
  `ice-rpc-nodejs`, name their proxies, `napi build`.
- The repository's example addon keeps serving `common`; it is the template.
- **Publication**: only `ice-rpc-nodejs` is published, on **crates.io**. The
  example addon and `common` stay in the repository; no example package is
  published to npm.
- Adding a service is a one-line edit in the addon; the compiler checks each name,
  and the same list drives `registerService` and `callService`, so they cannot
  drift.
- CI excludes `ice-rpc-nodejs` wherever it excludes `gateway-nodejs` (both need the
  N-API/Node toolchain), and the gateway job runs both crates' unit tests.

## Alternatives considered

| Alternative | Why not |
|---|---|
| Ship the addon with `common`'s list | Serves example services only; useless for a user |
| Publish a precompiled addon on npm | Same problem: the binary is tied to a fixed service set |
| `linkme` auto-discovery | Loses the explicit subset; depends on unproven napi-rs-in-rlib |
| Runtime plugins (`dlopen`) | A single universal binary, but a versioned C ABI and much more machinery |
| Promote `GatewayService` into `ice-rpc::json` | Possible, but no second consumer today (YAGNI) |
